# Titanic: feature engineering and XGBoost

A study of the Kaggle [Titanic: Machine Learning from Disaster](https://www.kaggle.com/competitions/titanic) data. Most of the work goes into the features: who travelled together, what the ticket number encodes, and whether port of embarkation matters once class is known. Two XGBoost models are then built on the features that survived testing.

Every notebook is committed with its outputs, so the results can be read on GitHub without running anything. Code cells are collapsed by default. Apart from `titles.ipynb`, each notebook is generated by a `build_*.py` script in the same folder, and the longer write-ups sit beside it in a `*_findings.py` file that the builder reads.

## Data

| File | Contents |
|---|---|
| `data/train.csv`, `data/test.csv`, `data/gender_submission.csv` | Original Kaggle files, unchanged |
| `data/complete_data.csv` | Train and test in one file (1,309 passengers), with `Dataset`, `FamilyId`, `FamilyCheck`, `Relatives` and `Deck` added. Every model reads this file |
| `data/complete_data.xlsx` | The same, train in blue text, test in red, engineered columns shaded |
| `data/train_families.csv`, `data/test_families.csv`, `data/families.xlsx` | The family columns for each dataset on its own |

Train and test are always used together for feature building, because Kaggle split families and ticket groups across the two files at random. Survival is only ever taken from train passengers, and never from the passenger being scored.

## Feature engineering

### Overview: [features/overview](features/overview)

`features_v1.ipynb` charts survival against every raw column in train.csv (891 passengers, 38% survived): counts and survival rate per group, with group sizes shown so small groups are not over-read.

### Titles: [features/titles](features/titles)

`titles.ipynb` extracts the title from `Name` and charts the number of passengers and the survival rate for every title in train. Title combines sex and age in one column, and separates boys (Master) from adult men. The models group it into Mr, Mrs, Miss, Master and Rare, with Mlle and Ms counted as Miss and Mme as Mrs.

### Families: [features/families](features/families)

SibSp and Parch give counts of relatives but not who they are. Families are rebuilt across all 1,309 passengers in three passes.

| Notebook | Method |
|---|---|
| `families_v1.ipynb` | Group by surname, ticket and cabin; a group is accepted when its size equals SibSp + Parch + 1 for every member |
| `families_v2.ipynb` | Relationship rules (sibling, spouse, parent, child) from SibSp and Parch, then matching on surname, maiden name, ticket, cabin, class, port and fare. Requires closed families |
| `families_v3.ipynb` | Drops the closed-family rule, builds households and checks each person instead. **497 of 519 passengers with family aboard (96%) are fully placed.** Writes the data files |
| `family_survival.ipynb` | Family survival by size, fare, deck, class and ticket type, and whether relatives share a survival component beyond their shared features |

The rules live in `family_logic.py`. Two standalone scripts sit alongside: `family_effect_check.py` measures how strongly relatives' model residuals correlate, by class, and `composition_features_check.py` tests household-composition flags (such as a woman travelling with husband and children). The composition flags add nothing to log loss or accuracy.

Conclusion: family is informative in itself. Relatives share survival that strangers with the same class, fare, ticket and cabin do not. The recommended features are the survival rate of a passenger's train relatives, and of female relatives in particular.

### Tickets: [features/tickets](features/tickets)

| Notebook | Question | Finding |
|---|---|---|
| `tickets_v1.ipynb` | What does the ticket encode? | Type mostly restates class and port. The number says far more: the leading digit of a 6-digit ticket is the class, and the number window predicts class for 98% of passengers and port for 88% |
| `tickets_model_v1.ipynb` | Is the ticket a useful model feature? | Lifts logistic regression from 79.6% to 81.8% accuracy (p = 0.01), but mostly through families on consecutive tickets. Same-ticket passengers share a deck 98% of the time |
| `tickets_residuals_v1.ipynb` | Do residuals from a ticket-free model cluster by ticket? | Same-ticket residuals correlate at 0.48. Number-range effects disappear once parties are counted once. Tickets 2 to 10 numbers apart keep a weak link (0.07 to 0.15) |
| `tickets_groups_v1.ipynb` | Ticket groups against families | 73% of same-ticket pairs are family. Once family survival is in the model, ticket survival adds nothing |

### Port of embarkation: [features/embarked](features/embarked)

`embarked_v1.ipynb`: Cherbourg passengers survived at 55% against 34% at Southampton, but most of the gap is class. With class, sex, age, family and fare in the model, port adds nothing detectable (likelihood-ratio p = 0.13, +0.5 points accuracy, p = 0.39).

### Deck: [features/deck](features/deck)

`add_deck.py` adds a `Deck` column: the first letter of the passenger's cabin or, where their own is blank, the most common deck among passengers on the exact same ticket. Exact ticket-mates agree on deck for 194 of 198 passengers; neighbouring ticket numbers do not, so no wider match is used. Run it after `build_families_v3.py`, which rewrites the data files without `Deck`.

## Models

All models are scored on holdouts that keep every family and ticket group within one fold (`StratifiedGroupKFold`), so the survival features never leak a holdout outcome.

### Engineered features used

- **Passenger**: Pclass, Title, Sex, Age, SibSp, Parch, HasCabin, Deck
- **Female-relative survival**: share of the passenger's mother, and for female passengers also sisters and daughters, who survived
- **Family survival**: share of all known relatives who survived
- **Ticket-mate survival**: share of other same-ticket passengers, outside the family, who survived

The survival features use train outcomes only and exclude the passenger's own outcome. They are blank where no such person is in train.

### XGBoost v1: [models/xgb_v1](models/xgb_v1)

8 feature sets x 445 hyperparameter settings x 3 holdouts, 10,680 models. Full write-up in [models/xgb_v1/README.md](models/xgb_v1/README.md).

- Female-relative survival is the feature that counts: median accuracy 81.8% to 84.1%
- Family survival adds a little more; ticket-mate survival, fare and port add nothing
- Feature choice matters far more than hyperparameters
- Final model: depth 6, 800 trees, learning rate 0.043. 85.5% on the 3 holdouts, best of 400 tries, so expect about 84%

### XGBoost v2: [models/xgb_v2](models/xgb_v2)

A smaller model to reduce overfitting: Deck and HasCabin dropped, trees 1 to 3 levels deep. 432 settings x 2 feature sets, scored on 20 holdouts (4 folds x 5 shuffles), 17,280 models.

- Picked: no ticket-mate survival, depth 2, 100 trees, learning rate 0.1
- 84.6% accuracy and 0.366 log loss averaged over 20 holdouts
- Predicts 38.8% of test passengers survive

## Reproducing

```
pip install -r requirements.txt

python features/families/build_families_v3.py     # writes data/complete_data.csv
python features/deck/add_deck.py                  # adds Deck
python features/tickets/build_tickets_v1.py       # any notebook builder, run from anywhere
python models/xgb_v1/build_xgb_v1.py              # 10,680 models, slow
python models/xgb_v1/build_submission_xgb_v1.py   # writes submission_xgb_v1.csv
python models/xgb_v2/build_xgb_v2.py              # writes submission_xgb_v2.csv
```

Each builder writes its notebook into its own folder and executes it. Builders ending `_v1` or `_v2` in `features/families` are superseded by `build_families_v3.py` and overwrite the data files if run. Built with Python 3.14.
